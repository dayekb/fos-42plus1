# Банк задач «Условная логика и пайплайны»

**Аннотация:** Задачи на проектирование цепочек промптов с ветвлением логики: определение формата входных данных, выбор соответствующего обработчика, fallback-сценарии, передача контекста между этапами и реализация feature-flags.

---

## Задача №1. Обработка разных форматов

**Условие:**  
Спроектируйте пайплайн из двух промптов:  
1. Определение формата входных данных (JSON, XML, CSV).  
2. Парсинг данных в единую структуру.  
Если формат не распознан (confidence < 0.7), вызовите fallback-промпт.

**Проверяемый результат:**  
- Правильно определён формат входных данных  
- Выбран корректный парсер для каждого формата  
- Fallback-сценарий срабатывает при низкой уверенности  
- Итоговые данные унифицированы  

**Сложность:** ★★★ (продвинутая)  

**Входные данные:**  
Три тестовых файла: `data.json`, `data.xml`, `data.csv`. Один из них невалидный.

**Эталон / подход к проверке:**  
Проверяется лог выполнения: на каком этапе сработал fallback, был ли выбран правильный промпт. Оценивается корректност

**Варианты параметризации:**  
- Добавить формат HTML  
- Добавить формат с ошибкой (отсутствие обязательного поля)  
- Усложнить схему (вложенные объекты)

---

## Задача №2. Передача контекста между этапами

**Условие:**  
Разработайте пайплайн из трёх шагов:  
1. Извлечение сущностей (ФИО, диагноз) из текста.  
2. Поиск соответствующих кодов МКБ-10.  
3. Формирование итогового отчёта в JSON.  
Контекст (извлечённые сущности) должен передаваться на следующие шаги.

**Проверяемый результат:**  
- Данные корректно передаются между этапами  
- На втором шаге используются данные первого  
- Итоговый отчёт содержит все сущности и коды  

**Сложность:** ★★★ (продвинутая)  

**Входные данные:**  
Текст медицинского заключения с диагнозом.

**Эталон / подход к проверке:**  
Проверяется, что на втором шаге модель получила диагноз и правильно подобрала код МКБ-10. Итоговый JSON содержит все поля.

**Варианты параметризации:**  
- Изменить тип сущностей (препараты, дозировки)  
- Добавить этап проверки (валидация кодов)  
- Усложнить текст (несколько диагнозов)

## Задача №3. Feature Flags и A/B-тестирование

**Условие:**  
Реализуйте пайплайн, который в зависимости от активного feature-флага использует либо старую версию промпта (A), либо новую (B). Логируйте, какая версия была применена, и собирайте метрики качества.

**Проверяемый результат:**  
- Feature-флаг корректно переключает версии  
- Логируются все вызовы  
- Сравниваются метрики (accuracy, latency)  

**Сложность:** ★★★ (продвинутая)  

**Входные данные:**  
Набор тестовых запросов (10 шт.) и конфигурация с флагом.

**Эталон / подход к проверке:**  
Проверяется, что при флаге `true` вызывается версия B, при `false` — A. Метрики собираются и агрегируются.

**Варианты параметризации:**  
- Добавить несколько флагов  
- Сделать A/B-тест с динамическим распределением трафика  
- Интегрировать с CI/CD

## Задача №4. Обработка ошибок и fallback

**Условие:**  
Спроектируйте пайплайн, который пытается выполнить запрос к основному промпту, но при возникновении ошибки (timeout, невалидный JSON) переключается на fallback-промпт, который возвращает упрощённый ответ. Все ошибки логируются.

**Проверяемый результат:**  
- Основной промпт выполняется при штатной работе  
- При ошибке срабатывает fallback  
- В логе зафиксирована причина переключения  

**Сложность:** ★★ (средняя)  

**Входные данные:**  
Тестовый запрос, на котором основной промпт даёт ошибку (например, слишком длинный текст).

**Эталон / подход к проверке:**  
Проверяется, что пайплайн не падает, а возвращает fallback-ответ. В логе есть запись об ошибке.

**Варианты параметризации:**  
- Добавить несколько уровней fallback  
- Эмулировать разные типы ошибок  
- Изменить fallback-поведение (повторить попытку)
