### 📌 Вопрос 1. Паттерны агентов (ReAct)

| Параметр | Значение |
|----------|----------|
| **Уровень** | L1 🟢 (Низкая) |
| **Тип** | 🔘 Одиночный выбор |
| **Тема** | Паттерны агентов |

**Вопрос:**  
Какой паттерн предполагает цикл «Рассуждение → Действие → Наблюдение» (Reasoning + Acting) для решения задачи?

**Варианты ответов:**
- A) Plan&Solve
- B) ReAct ✅
- C) MCP (Model Context Protocol)
- D) RAG

> **Правильный ответ:** **B) ReAct**

**Пояснение:**  
Паттерн **ReAct** (Reasoning + Acting) основан на чередовании рассуждений и действий: агент делает шаг рассуждения, выполняет действие, наблюдает результат и повторяет цикл. Это отличает его от Plan&Solve, где сначала строится полный план, а затем он выполняется.

### 📌 Вопрос 2. Паттерны агентов (Plan&Solve)

| Параметр | Значение |
|----------|----------|
| **Уровень** | L1 🟢 (Низкая) |
| **Тип** | 🔘 Одиночный выбор |
| **Тема** | Паттерны агентов |

**Вопрос:**  
В каком сценарии наиболее эффективно применение паттерна Plan&Solve вместо ReAct?

**Варианты ответов:**
- A) Когда задача требует постоянного взаимодействия с пользователем
- B) Когда задача хорошо структурирована и может быть разбита на фиксированные шаги ✅
- C) Когда требуется обработка потоковых данных в реальном времени
- D) Когда агент должен динамически адаптироваться к изменяющимся условиям

> **Правильный ответ:** **B) Когда задача хорошо структурирована и может быть разбита на фиксированные шаги**

**Пояснение:**  
**Plan&Solve** подходит для задач, где можно заранее построить детальный план выполнения, например, создание отчёта по шаблону или выполнение регламентной операции. ReAct лучше для динамических, недетерминированных сценариев.

| Параметр | Значение |

**Вопрос:**  
Какие из перечисленных практик являются рекомендуемыми при интеграции LLM-агента с внешними API? *(выберите все верные)*

**Варианты ответов:**
- A) Синхронный вызов всех API без таймаутов
- B) Кэширование ответов для часто повторяющихся запросов ✅
- C) Реализация механизма повторных попыток (retry) с экспоненциальной задержкой ✅
- D) Использование песочницы (sandbox) для изоляции выполнения кода от внешних API ✅

### 📌 Вопрос 10. Интеграция с Kafka и обработка событий

| Параметр | Значение |
|----------|----------|
| **Уровень** | L3 🔴 (Высокая) |
| **Тип** | ✍️ Открытый вопрос |
| **Тема** | Интеграция с Kafka |
| **Кейс** | «Агент управления ценами (Kafka-триггер)» |

**Вопрос:**  
Опишите архитектуру агента-консьюмера для обработки событий изменения цен. Как обеспечить обработку сообщений без потерь и как реализовать механизм повторной обработки при сбоях?

> **Примерный правильный ответ:**

```
Агент должен использовать Kafka Consumer с ручным подтверждением 
смещения (manual commit). 

При получении сообщения цена обновляется в онлайн-каталоге; 
в случае успеха смещение подтверждается. 

При ошибке (например, временная недоступность каталога) 
сообщение не подтверждается, а повторная попытка выполняется 
через механизм retry (с экспоненциальной задержкой) в рамках 
той же партиции. 

При постоянных ошибках сообщение отправляется в dead-letter 
topic для последующего анализа. 

Также следует настроить мониторинг lag-а для обнаружения 
накопления необработанных сообщений.
```

### 📌 Вопрос 20. Мультиагентные системы и эскалация

| Параметр | Значение |
|----------|----------|
| **Уровень** | L3 🔴 (Высокая) |
| **Тип** | ✍️ Открытый вопрос |
| **Тема** | Мультиагентные системы |
| **Кейс** | «Агент модерации отзывов» |

**Вопрос:**  
Предложите архитектуру мультиагентной системы для модерации отзывов, включая распределение ролей между агентами, их взаимодействие и механизм эскалации.

> **Примерный правильный ответ:**

```
Архитектура может включать:

1. Агент-анализатор: принимает отзыв, выделяет сущности и 
   проводит первичную оценку тональности.

2. Агент-детектор копипасты: сравнивает текст с векторной БД 
   опубликованных отзывов, вычисляет сходство.

3. Агент-классификатор: определяет, является ли текст шаблонным 
   или сгенерированным ИИ (использует отдельную модель).

4. Агент-принимающий решение: агрегирует результаты всех агентов, 
   вычисляет общий риск. Если риск ниже порога — публикует; 
   если выше — эскалирует на ручную модерацию.

5. Агент-аудитор: логирует все решения и при необходимости 
   позволяет человеку-модератору вносить коррективы, которые 
   затем могут использоваться для дообучения агентов (feedback loop).

Взаимодействие: асинхронное через брокер сообщений, каждый агент 
может работать независимо, результаты передаются дальше.
```
