# 📊 Скрипты оценки качества (Evaluation)

Данная папка содержит инструменты для автоматизированного измерения качества поисковых и генеративных компонентов RAG-пайплайна. Основной фокус сделан на сравнении базовой (`Baseline`) и оптимизированной (`Optimized`) версий системы.

## 📁 Структура папки

```text
evaluation/
├── test_queries.json      # Тестовый датасет: пары "запрос → релевантные документы"
├── metrics.py             # Математические функции расчёта метрик (Recall, MRR, NDCG)
└── auto_check.py          # Главный скрипт запуска сравнения и валидации (PASS/FAIL)
```

## ⚙️ Зависимости

Для работы скриптов оценки убедитесь, что установлены следующие библиотеки (помимо базовых зависимостей проекта):
```bash
pip install numpy
```
*Примечание: Скрипты предполагают, что класс `OptimizedRAGPipeline` доступен для импорта из модулей `src`.*

Для запуска автоматической оценки качества выполните команду из корневой директории проекта:

## 📄 Описание файлов

### 1. `test_queries.json`
Формат тестового датасета. Содержит список запросов и ID документов, которые считаются релевантными для данного запроса.

**Пример структуры:**
```json
[
  {
    "query": "Как настроить асинхронную обработку в FastAPI?",
    "relevant_doc_ids": ["doc_fastapi_async.pdf", "doc_uvicorn_tips.txt"]
  },
  {
    "query": "Какие гиперпараметры влияют на сходимость SGD?",
    "relevant_doc_ids": ["doc_sgd_params.pdf"]
  }
]
```
*Рекомендация: Для статистической значимости датасет должен содержать не менее 20–50 разнообразных запросов.*

### 2. `metrics.py`
Модуль с реализацией стандартных метрик информационного поиска:
* **`recall_at_k`**: Доля релевантных документов, попавших в топ-$k$ результатов.
* **`mrr_at_k`** (Mean Reciprocal Rank): Обратный ранг первого найденного релевантного документа.
* **`ndcg_at_k`** (Normalized Discounted Cumulative Gain): Учитывает позицию релевантных документов (чем выше, тем лучше).
* **`evaluate_retriever`**: Обёртка, которая прогоняет функцию-ретривер по всему `test_queries.json` и возвращает усреднённые значения метрик.

### 3. `auto_check.py` (Главный валидатор)
Скрипт, который автоматически сравнивает две конфигурации пайплайна.

**Логика работы:**
1. Загружает `test_queries.json`.
2. Считает baseline чистым Dense-поиском по индексу из ЛР 2.2.
3. Инициализирует `OptimizedRAGPipeline` (гибридный поиск + RRF + реранкинг + query rewriting из ЛР 2.3).
4. Вычисляет `Recall@5` для обоих пайплайнов.
5. Рассчитывает процент улучшения:  
   `improvement = ((Optimized - Baseline) / Baseline) * 100`

**Критерий успешного прохождения (PASS):**
Скрипт вернёт код выхода `0` (успех), если выполнено **хотя бы одно** из условий:
1. Улучшение `Recall@5` составляет **≥ 15%** относительно базовой линии.
2. Абсолютное значение `Recall@5` для оптимизированного пайплайна **≥ 0.85**.

В противном случае скрипт вернёт код выхода `1` (ошибка) и рекомендации по доработке. Результаты также сохраняются в файл `experiments/evaluation_results.json`.

## 🛠️ Типичные ошибки и как их исправить (Troubleshooting)

Если `auto_check.py` выдаёт `❌ АВТОПРОВЕРКА НЕ ПРОЙДЕНА`, проверьте следующие моменты:

| Симптом | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Optimized хуже Baseline** | Некорректная токенизация в BM25 для русского языка. | Используйте `pymorphy2` или `nltk` для лемматизации перед BM25, а не просто `split()`. |
| **Optimized хуже Baseline** | Неправильный коэффициент $k$ в формуле RRF. | Убедитесь, что константа `k_rrf` установлена в значение `60` (стандарт индустрии). |
| **Слишком долго работает** | Cross-encoder обрабатывает слишком много документов. | Уменьшите количество кандидатов, подаваемых на реранкер, до `top-20` или `top-50`. |
| **Query Rewriting ухудшает поиск** | LLM переписывает запрос до неузнаваемости или галлюцинирует. | Установите `temperature=0.1` в промпте рерайтера и ужесточите инструкцию ("выведи только запрос"). |
| **Нечестное сравнение** | В Baseline и Optimized используются *разные* модели эмбеддингов. | Зафиксируйте одну и ту же модель (например, `BGE-M3`) для обоих прогонов. |

## 👨‍🏫 Для преподавателей / проверяющих

Для быстрой верификации работы студента достаточно:
1. Убедиться, что в репозитории присутствует файл `experiments/evaluation_results.json`.
2. Открыть его и проверить поле `"pass": true`.
3. При необходимости запустить скрипт локально: `python evaluation/auto_check.py`.
4. Если студент утверждает, что внедрил свою уникальную оптимизацию (бонусные баллы), попросите его запустить **Ablation Study** (поочерёдное отключение компонентов: только BM25, только Rerank, только Rewriting), чтобы доказать вклад каждого элемента в итоговый прирост метрик.
