## 🔹 СР №1. Диагностика метрик: когда цифры обманывают

**Цель:** Научиться интерпретировать автоматические метрики и выявлять их ограничения на контрастных примерах.

### Задание
Вам предоставляются **10 пар** «эталонный ответ – сгенерированный ответ» (задача: суммаризация новостей). Для каждой пары:

1. Вычислите значения метрик: **BLEU-1, BLEU-4, ROUGE-L, METEOR, BERTScore**.
2. Определите **минимум 3 примера**, где метрики дают парадоксальный результат (высокий BLEU при плохом смысле, низкий ROUGE при хорошем пересказе и т.д.).
3. Для каждого такого примера напишите **диагностическую карту**:
   - *«Что показывает метрика?»*
   - *«Что на самом деле с ответом?»*
   - *«Почему возникло расхождение?»*
4. Предложите **комбинированное правило** (например, пороговое условие `if BLEU > 0.4 and BERTScore < 0.7: trigger manual check`), которое позволит автоматически выявлять подозрительные ответы.

### Индикаторы выполнения

| № | Индикатор | Описание |
|---|-----------|----------|
| 1.1 | Расчёт метрик | Все 10 пар обработаны, метрики сведены в таблицу. |
| 1.2 | Выявление аномалий | Выявлено минимум 3 случая расхождения метрик и семантики. |
| 1.3 | Глубина анализа | В каждой диагностической карте указана первопричина (синонимия, инверсия, избыточность, фактологическая ошибка). |
| 1.4 | Практический фильтр | Предложено правило-триггер для автоматической фильтрации сомнительных ответов. |
| 1.5 | Визуализация | Построен scatter-plot (например, BLEU vs BERTScore) с выделением аномалий. |

### Формат сдачи
- Отчёт с таблицами, графиками и выводами.

## 🔹 СР №2. Проектирование и калибровка LLM-as-a-Judge

**Цель:** Создать устойчивый оценочный промпт, научиться собирать оценки и проводить базовую калибровку.

### Задание
1. **Разработайте рубрику** по 4 критериям (например: *Факты, Полнота, Стиль, Безопасность/Токсичность*) с дескрипторами для каждого уровня (1–5).
2. **Напишите промпт** для LLM-судьи, который принимает эталон и ответ, возвращает строгий JSON с оценками и комментарием.
3. **Реализуйте функцию** на Python, которая:
   - отправляет промпт в API (или локальную модель);
   - парсит JSON;
   - вычисляет **взвешенную агрегированную оценку** (веса задаются конфигом).
4. **Проведите калибровку**: возьмите 20 примеров, получите оценки судьи и сравните их с экспертной оценкой (или синтетической «истиной»). Вычислите **среднюю абсолютную ошибку (MAE)**.
5. **Итеративно улучшите промпт**: если MAE > 0.7, измените инструкцию, уточните дескрипторы и повторите замер.

### Индикаторы выполнения

| № | Индикатор | Описание |
|---|-----------|----------|
| 2.1 | Рубрика | Чёткие, недвусмысленные дескрипторы для всех 4 критериев. |
| 2.2 | Промпт | Промпт содержит явное требование JSON-схемы и примеры (few-shot). |
| 2.3 | Код | Функция обрабатывает ошибки парсинга, тайм-ауты, возвращает дефолтные значения при сбое. |
| 2.4 | Калибровка | Проведён цикл «оценка → анализ MAE → улучшение промпта» (минимум 2 итерации). |
| 2.5 | Документация | Задокументированы изменения промпта и их влияние на MAE. |

### Формат сдачи
- Jupyter Notebook с кодом и выводами.
- Лог-файл версий промпта.

## 🔹 СР №3. Мониторинг качества в продуктивной среде (Data Drift & Metrics Drift)

**Цель:** Научиться отслеживать деградацию качества LLM-сервиса во времени без эталонов на потоке.

### Задание
Вам предоставляется **смоделированный поток логов** (1000 записей) за 30 дней от чат-бота службы поддержки. Логи содержат: `timestamp`, `user_query`, `bot_response`, `response_time`, `token_usage`.

1. **Организуйте мониторинг** без эталонов (reference-free):
   - Для каждого ответа вычисляйте **перплексию** (через API или локальную модель) и **токсичность** (через `transformers`).
   - Вычисляйте **длину ответа** и **время генерации**.
2. **Постройте временные ряды** для каждой метрики (daily aggregates: среднее, 95-й перцентиль).
3. **Реализуйте детекцию дрейфа**:
   - Используйте **PSI (Population Stability Index)** для распределения длин/перплексии по неделям.
   - Используйте **CUSUM** или **скользящее контрольное окно** для обнаружения резких скачков.
4. **Настройте алерты**: если PSI > 0.2 или время ответа выросло на 30% за 2 дня – отправляется уведомление (имитация в консоль).
5. Визуализируйте дашборд (статический Plotly или `matplotlib` с аннотациями точек дрейфа).

### Индикаторы выполнения

| № | Индикатор | Описание |
|---|-----------|----------|
| 3.1 | Извлечение признаков | Реализован скрипт для расчёта перплексии и токсичности для всего потока. |
| 3.2 | Агрегация | Построены суточные агрегированные ряды (минимум 3 метрики). |
| 3.3 | Детекция дрейфа | Реализован расчёт PSI между недельными срезами и/или CUSUM-алгоритм. |
| 3.4 | Алерты | Логика алертов привязана к конкретным порогам, задокументирована. |
| 3.5 | Визуализация | Графики с выделением точек срабатывания алертов. |

### Формат сдачи
- Архив с кодом и сгенерированным HTML-отчётом (или PDF с графиками).

## 🔹 СР №4. Экономическая оценка и оптимизация затрат LLM-сервиса

**Цель:** Научиться оценивать TCO (совокупную стоимость владения) LLM-решения и находить оптимальный баланс «цена-качество».

### Задание
Вам дана гипотетическая задача: **ежедневный объём запросов – 100 000**, средняя длина входа – 500 токенов, выхода – 200 токенов. Требуется выбрать модель/архитектуру для решения и оценить затраты.

1. **Проанализируйте рыночные варианты** (на основе открытых цен):
   - Вариант А: Проприетарное API (например, GPT-4o или YandexGPT API).
   - Вариант Б: Open-source модель (например, LLaMA-3-70B), развёрнутая на собственных GPU (AWS/Azure/Yandex Cloud).
   - Вариант В: Дистиллированная/квантованная модель (LLaMA-3-8B-Q4) на дешёвом инстансе.
2. **Рассчитайте** для каждого варианта:
   - **Операционные затраты в месяц** (API-стоимость или стоимость аренды инстансов).
   - **Latency** (приблизительно, исходя из известных бенчмарков).
   - **Качество** (присвойте гипотетический балл F1/Accuracy на основе открытых лидербордов).
3. **Постройте модель «стоимость vs. качество»** и определите **Pareto-фронт**.
4. Напишите **рекомендацию** для бизнеса с учётом:
   - бюджета в $5,000/мес;
   - требования к задержке < 2 сек;
   - необходимости соблюдения 152-ФЗ (данные не должны покидать РФ).
5. Опишите сценарий **масштабирования**: что изменится при росте до 1 млн запросов/день?

### Индикаторы выполнения

| № | Индикатор | Описание |
|---|-----------|----------|
| 4.1 | Сбор данных | Приведены конкретные цифры стоимости токенов/часов инстансов с источниками. |
| 4.2 | Расчёты | Подробные таблицы затрат для 3 вариантов (операционные + CAPEX, если применимо). |
| 4.3 | Pareto-анализ | График «Cost vs. Quality» с выделением оптимального варианта. |
| 4.4 | Рекомендация | Чёткая рекомендация с привязкой к бюджету и регуляторным ограничениям. |
| 4.5 | Масштабирование | Описана точка безубыточности перехода с API на собственный GPU-кластер. |

### Формат сдачи
- Аналитическая записка (1–2 страницы) с таблицами и графиками.
