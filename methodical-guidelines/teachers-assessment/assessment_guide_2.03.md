# ⚙️ Методика проверки: Лабораторная работа 2.3 (Оптимизация RAG)

**Компетенции:** LLM-3 (3.4, 3.5), LLM-1 (1.2)  
**Особенность:** Работа включает скрипт автоматической метрической проверки (`evaluation/auto_check.py`).

## Логика автоматической проверки (PASS / FAIL)
Скрипт сравнивает метрики `Baseline` (чистый dense-поиск из ЛР 2.2) и `Optimized` (гибридный поиск + реранкинг + query rewriting).

**Условие успешного прохождения (PASS):**
1. Улучшение Recall@5 составляет **≥ 15%** относительно базовой линии, **ИЛИ**
2. Абсолютное значение Recall@5 для оптимизированного пайплайна **≥ 0.85**.

*Если условие не выполнено, скрипт выдает FAIL и рекомендации.*

## Критерии ручного оценивания (100 баллов)

| Компонент реализации | Баллы | Что проверяет преподаватель |
| :--- | :---: | :--- |
| **BM25-ретривер** | 15 | Корректная токенизация (учет русского языка), индексация корпуса. |
| **Гибридный поиск (RRF)** | 20 | Правильная реализация формулы RRF (обычно с k=60), объединение рангов. |
| **Реранкинг (Cross-encoder)**| 20 | Использование модели (напр., `ms-marco-MiniLM-L-6-v2`), применение только к top-N кандидатам (оптимизация скорости). |
| **Query Rewriting** | 15 | Наличие модуля переформулирования (LLM или rule-based), кэширование результатов. |
| **Сборка пайплайна** | 10 | Корректная интеграция всех компонентов в единый класс/функцию. |
| **Результат автопроверки** | 10 | Скриншот или лог успешного прохождения (`✅ АВТОПРОВЕРКА ПРОЙДЕНА`). |
| **Анализ в отчете** | 10 | Выводы о влиянии каждой техники (Ablation study) и компромиссах (latency). |

## 🛠️ Действия преподавателя при FAIL автопроверки
Если студент присылает отчет с FAILED, проверьте:
1. Использует ли он **одну и ту же** модель эмбеддингов для Baseline и Optimized (сравнение должно быть честным).
2. Корректно ли работает токенизация в BM25 для русского языка (рекомендовать `pymorphy2` или `nltk`).
3. Не "сломал" ли Query Rewriting исходный запрос (проверить temperature=0.1 и строгий промпт).
