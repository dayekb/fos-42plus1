1. ФИО → `[ФИО]`
2. Дата рождения → скрыть день, оставить месяц и год


#### Задание 3. «Универсальный переводчик»: Унификация расписания

**Время:** 40 минут  
**Индикаторы:** 5.4

**Постановка задачи:** Система интегрируется с 5 внешними медицинскими сервисами. Каждый передаёт расписание в своём формате (JSON, XML, CSV, YAML, произвольный текст).

**Разработайте цепь промптов для:**
1. **Детектор формата** — определение типа входных данных.
2. **Парсер** — извлечение данных в промежуточный формат.
3. **Нормализатор** — приведение к единой структуре:
   ```json
   {
     "doctor_id": "string",
     "doctor_name": "string",
     "date": "YYYY-MM-DD",
     "time_start": "HH:MM",
     "time_end": "HH:MM",
     "status": "available|booked|blocked",
     "source_system": "string"
   }
   ```
4. **Матчер** — сопоставление врачей из разных систем с внутренней базой.
5. **Валидатор** — проверка обязательных полей и логических противоречий.

**Требования:**
- Цепочка должна быть расширяемой (добавление нового формата ≤ 1 промпт).
- Обработка ошибок парсинга с `graceful degradation`.
- Логирование проблемных записей.

**Примеры входных данных:**

Формат 1 (JSON):
```json
{"doctor": "Иванов И.И.", "slot": "2024-03-15 14:00-14:30", "free": true}
```

Формат 2 (CSV):
```csv
doctor_name,date,time,duration,status
"Петрова М.С.",15.03.2024,14:00,30,available
```

Формат 3 (текст):
```
Доктор: Сидоров А.П.
Приём: 15 марта 2024, с 10:00 до 11:00
Статус: свободен
```

#### Задание 4. «Фейк-контроль»: Проверка достоверности отзывов

1. Текст отзыва (тональность, детализация, уникальность).
2. Профиль пользователя (история отзывов, активность).
3. Метаданные (время публикации, IP, устройство).
4. Изображения (если прикреплены фото — анализ на уникальность).

**Задача:** Создать систему оценки риска недостоверности:

**Признаки для анализа:**
- 🚩 Шаблонный текст (повторы фраз, стандартные конструкции).
- 🚩 AI-генерация (слишком грамотный, без эмоций).
- 🚩 Копипаста (совпадение с другими отзывами).
- 🚩 Подозрительная активность (много отзывов за короткое время).
- 🚩 Несоответствие фактам (отзыв о приёме, которого не было).

**Выходные данные:**
```json
{
  "risk_level": "high|medium|low",
  "risk_score": 0.0-1.0,
  "flags": ["шаблонный текст", "AI-генерация"],
  "similarity_matches": [{"review_id": "123", "similarity": 0.95}],
  "recommendation": "publish|moderate|reject",
  "explanation": "текстовое обоснование"
}
```

**Дополнительно:** Добавьте «режим объяснений» — когда система генерирует понятный ответ для модератора:
```
Этот отзыв подозрителен: 85% текста совпадает с отзывом пользователя #456 
от 10.03.2024. Также пользователь оставил 15 отзывов за последние 2 дня. 
Рекомендуется отклонить.
```

#### Задание 5. «Сейф-доктор»: Безопасная передача документов

**Время:** 30 минут  
**Индикаторы:** 5.4

**Сценарий:** Пациент хочет передать врачу медицинские документы перед консультацией. Нужен умный механизм контроля доступа.

**Разработайте цепь промптов:**

**Этап 1: Классификация чувствительности**
```
Проанализируй документ и определи уровень чувствительности:

УРОВЕНЬ 1 (Публичный):
- Общие рекомендации
- Информационные материалы

УРОВЕНЬ 2 (Внутренний):
- Результаты анализов
- Направления

УРОВЕНЬ 3 (Конфиденциальный):
- Психиатрические заключения
- ВИЧ-статус
- Генетические тесты

УРОВЕНЬ 4 (Строго конфиденциальный):
- Паспортные данные
- СНИЛС, ИНН
- Финансовая информация
```

**Этап 2: Определение срока доступа**
```
Условная логика:
- Уровень 1 → до 30 дней
- Уровень 2 → до 7 дней
- Уровень 3 → до 24 часов
- Уровень 4 → только на время консультации (4 часа)

Если документ содержит ПДн → минимальный срок
Если запрошено несколько документов → срок по максимальному уровню
```

**Этап 3: Генерация объяснения для пациента**
```
Сформируй понятное сообщение:

«Вы передаёте доктору [ФИО врача]:
✓ Результаты анализов (доступ 7 дней)
⚠️ Паспортные данные (доступ 4 часа)
⚕️ Врач сможет просмотреть документы до [дата и время].
🔒 После этого доступ автоматически закроется.
❌ Вы можете отозвать доступ в любой момент в разделе "Мои документы".»
```

**Этап 4: Логирование и аудит**

Зафиксировать: кто передал, кому, какие документы, срок доступа, время создания ссылки, уникальный идентификатор доступа.

#### Задание 6. «Фото-доктор»: Улучшение качества изображений

**Время:** 35 минут  
**Индикаторы:** 5.4, 5.7

**Мультимодальная задача:** Пациенты загружают фото документов через смартфон. Часто качество плохое.

**Разработайте промпт, который:**

1. **Анализирует качество** по шкале 1–10:
   - Освещение (1 = слишком тёмно/яркое, 10 = равномерное).
   - Угол съёмки (1 = сильный перекос, 10 = перпендикулярно).
   - Резкость (1 = размыто, 10 = чётко).
   - Наличие бликов/теней.
   - Полнота кадра.

2. **Формирует инструкции для коррекции:**
   - Если угол < 7 → «Выпрямить документ (поворот на X градусов)».
   - Если освещение < 6 → «Улучшить контраст, применить auto-levels».
   - Если резкость < 5 → «Применить sharpening filter».
   - Если есть тени → «Устранить тени алгоритмом CLAHE».

3. **Оценивает читаемость текста** после обработки.

4. **Выдаёт рекомендацию:**
   ```json
   {
     "quality_score": 7.5,
     "accept": true,
     "corrections_applied": ["deskew: 12°", "contrast: +30%"],
     "text_readability": 0.92,
     "user_message": "Отлично! Документ принят."
   }
   ```
   ИЛИ
   ```json
   {
     "quality_score": 3.2,
     "accept": false,
     "corrections_applied": [],
     "text_readability": 0.34,
     "user_message": "Фото слишком тёмное и размытое. Пожалуйста, сфотографируйте заново при хорошем освещении, держа камеру прямо над документом."
   }
   ```

**Требования:**
- Пороговые значения: `score ≥ 6` → принять, `4–6` → обработать, `< 4` → переснять.
- Формировать понятные подсказки для пользователя.
- Поддерживать разные типы документов (горизонтальные/вертикальные).

```
↓
Финальный результат
```

**Требования:**
- Реализовать цикл обратной связи (максимум 2 итерации).
- Логировать все переходы между этапами.
- Предусмотреть выход по таймауту.

### Критерии оценивания практического занятия

| Критерий | Баллы | Описание |
|---|---|---|
| Корректность архитектуры | 0–4 | Правильное построение цепочки промптов |
| Условная логика | 0–3 | Корректная реализация if-then-else |
| Обработка ошибок | 0–3 | Graceful degradation, fallback сценарии |
| Мультимодальность | 0–3 | Корректная работа с изображениями |
| Структура выхода | 0–2 | Валидный JSON/XML, соответствие схеме |
| Оптимизация | 0–2 | Минимизация этапов без потери качества |
| Документация | 0–2 | Комментарии, пояснения к промптам |
| Тестирование | 0–1 | Проверка на тестовых данных |

**Итого:** 20 баллов  
**Шкала перевода:** 18–20 — отлично, 14–17 — хорошо, 10–13 — удовлетворительно, <10 — неудовлетворительно.
